# 05 — What the i.MX95 debug path gives that the T113-S3 can't

**Basis:**
- **i.MX95:** measured on the FRDM-IMX95-PRO on 2026-10-16 (docs 01–04).
- **T113-S3:** the elb1 repo's records (`6.host-tools/jtag-ch347/README.md`, `4.docs/2.status/56`, `80`).

**Tags:** `[V]` measured · `[elb1]` recorded in the elb1 repo · `[?]` not verified.

## 1. Side by side

| | T113-S3 (LCPI-PC, MQ-Dual) | i.MX95 (FRDM-IMX95-PRO) |
|---|---|---|
| Cores | 2× Cortex-A7 (ARMv7), C906 (RISC-V), HiFi4 `[elb1]` | 6× Cortex-A55 (ARMv8.2, AArch64, Linux at EL2/VHE), M7, M33 (System Manager) `[V]` |
| JTAG pins | the microSD slot's pins (PF0/1/3/5), through a sniffer; no SD card while debugging; switched over FEL `[elb1]` | dedicated DAP pads, shared only with LPUART5 (Bluetooth); usable with Linux and its storage running once LPUART5 is off (`board/mkdtb.sh`) `[V]` |
| Debug access | open | **open in serial download** on this OEM-open part; an authentication path exists (debug mailbox, signed DAT) for closed parts `[V]` |
| APs | AHB-AP, APB-AP `[elb1]` | AHB-AP, APB-AP, M7, M33, **MDM-AP**, GPU, NPU (RM Table 77; AP 0/1/6 read `[V]`) |
| **Instruction trace** | **none**: the A7s' ETMs are marked absent and read 0 `[elb1]` | **ETMv4.2 per A55 → ETF 16 KB → ETR into DRAM; 1.58 GiB captured in 8 s and decoded with 0 errors** `[V]` |
| Trace buffer size | — | anything in DRAM; 2 GB reserved today; 16 GB on the board `[V]` |
| PC sampling without halting | DBGPCSR, with OpenOCD change 4, ~10,400 samples/s `[elb1]` | PMPCSR (ARMv8.2, in the PMU block), stock registers, used today `[V]` |
| Core state from outside | through each core's debug registers | **MDM-AP**: every A55's halted/WFI/WFE bit plus the M7 and M33 in one register, no core touched `[V]` |
| Reset from the debugger | watchdog register over the AHB-AP (`jtag-reset.sh`) `[elb1]` | **MDM-AP `JTAG_SW_RST` → SRC full SoC reset**, no system bus needed `[V]` |
| A second console with system rights | — | **the System Manager monitor (M33)**: pad mux, clock roots, power domains, SRC, BLK_CTRL, PMICs, reset; it diagnosed and reset a board whose A55 and debug APs were gone `[V]` |
| Debugger's memory view | all DRAM (128/256 MB) | **only the low 4 GB of 16 GB** (AHB-AP 32-bit, CFG.LA = 0); above that only through Linux or a halted core `[V]` |
| USB boot ROM | **FEL**: read, write and execute anywhere, unsigned `[elb1]` | **SDP**: accepts a boot container and runs it; no peek/poke `[V]` (uuu `SDPS: boot`) |
| Memory map seen by the debugger | the CPU's | **offset**: CoreSight `0x4xxxxxxx` (RM) is `0x8xxxxxxx` on the APB-AP `[V]` |

## 2. What that buys in practice

1. **Instruction trace is the big one.**
   - On the T113, "what ran" can only be sampled: PC sampling, or halting.
   - On the i.MX95 every executed instruction of a core can be recorded into DRAM for seconds, then decoded, e.g. 200 M instructions per 16 MB ([04](04-arm-trace-into-dram.md)).
   - With address-range filters, a probe path like the DSI/ATTINY one could be recorded completely across a boot. `[?]`
2. **External state without perturbation.** MDM-AP plus PMPCSR showed "panic", "idle" and "busy in `clear_user`" without stopping a core.
3. **A reset you can reach when everything else is gone:**
   - from JTAG (MDM-AP), unless the APs themselves fail;
   - from the SM's UART otherwise.
4. **Firmware-level visibility:** the SM sees and changes what Linux can't (pad mux, clock roots, Q-channels). In [03](03-dsi-and-the-i2c-fault.md) that split the I2C problem into "the bus" and "the controller" with a few reversible register writes.

## 3. Where the T113 is easier

- **FEL** is a better bare USB tool than SDP. You can load and run anything anywhere, and `jtag-to-fel.sh` drops a running T113 back into it.
- **The i.MX95 equivalent is SDP plus the open debug port:**
  - the debugger works while the ROM waits;
  - U-Boot's fastboot over uuu gives the command channel;
  - `JTAG_SW_RST` with SW4 on serial download returns to SDP in about 1 s.
- **The whole DRAM is visible to the debugger** on the T113. The i.MX95 needs Linux (`physwin`) above 4 GB.
- **No firmware in the way:** the i.MX95's TRDC, the SM, SCMI pin control and the ELE add layers that can fence things off, like the A55's own access to the ETF.

## 4. "SDP is like FEL, right?" — partly

| | FEL (Allwinner BROM) | SDP (i.MX95 ROM) |
|---|---|---|
| Entry | no bootable media, or FEL button | SW4 = serial download (x,OFF,OFF,ON) |
| What it accepts | arbitrary read/write/exec commands | a boot image (container with the OEI, SM and SPL/U-Boot) |
| Peek/poke | yes | no; but here the debug port is open in that state |
| What we use | `sunxi-fel`, `xfel` | `uuu` with `ramboot.lst` (U-Boot from RAM, fastboot) |
| Back into it without a button | `jtag-to-fel.sh` (JTAG) | MDM-AP `JTAG_SW_RST` or `smmon.py reset`, with SW4 on serial download |

**Watch out:** a warm `reboot` from a RAM-booted Linux with SW4 on serial download sends SPL into a USB-SDP fault loop (yocto memory, 2026-09-15). Use the SM or JTAG reset instead, which re-run the ROM.
